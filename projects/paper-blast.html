Paper Blast

I wanted to blow up my reading list, so I built a game where you can. Paper Blast is a 2D platformer in Unity where any PDF you import becomes destructible terrain.

Studying Game Studies means a lot of PDFs. Somewhere between another paper and another learning diary, "what if I could blow this up?" became a prototype.

You jump across lines of text, blast through paragraphs and fall into the next page. Rockets, lasers, a black hole and an eraser help with the demolition. Some of the letters you blast loose gather into enemies and fight back.

The biggest technical challenge was working with layouts that were never designed to be levels. The document gives me the layout. My job is to turn it into something playable.

Technical challenges

Turning a document into a level

Each page is rendered to pixels and analysed. Every text line gets a one-way platform along its top, so you can jump up through it and land on it. Images, tables and formulas become solid blocks.

Scanned pages have no text layer, so an image-based fallback finds line-shaped ink instead: it bridges small gaps along each row and joins touching runs into blocks.

While you play a page, the next one is prepared on a background thread so page turns don't stall. If no PDF is loaded, a seeded generator writes one, so the game always has something to play.

Keeping what you see and what you collide with in sync

The page has two layers: the visible pixels and a collision mask of the same size. A blast clears both in the same loop, so they can never disagree. Re-uploading a whole page texture after every explosion would be far too slow, so the terrain marks only the chunks that changed. The view then copies those chunks to the GPU with a fixed budget per frame. The chunk tracker is preallocated, so blasting never allocates memory.

public void Carve(CarveShape shape)
{
    var bounds = shape.PixelBounds;
    var xMin = Mathf.Max(0, bounds.xMin);
    var yMin = Mathf.Max(0, bounds.yMin);
    var xMax = Mathf.Min(Width, bounds.xMax);
    var yMax = Mathf.Min(Height, bounds.yMax);
    if (xMin >= xMax || yMin >= yMax)
        return;

    var changed = false;
    for (var y = yMin; y < yMax; y++)
    {
        var row = y * Width;
        for (var x = xMin; x < xMax; x++)
        {
            if (!shape.Contains(x, y))
                continue;

            var i = row + x;
            if (_visual[i].a == 0 && _collision[i] == CollisionCell.Empty)
                continue;

            // Visual and collision layers change together.
            _visual[i] = Hole;
            _collision.ClearAt(i);
            changed = true;
        }
    }

    if (changed)
        Chunks.MarkDirty(new RectInt(xMin, yMin, xMax - xMin, yMax - yMin));
}

private void LateUpdate()
{
    if (_terrain == null || _terrain.Chunks.DirtyCount == 0)
        return;

    // Upload at most one staging texture's worth
    // of chunks per frame; the rest wait their turn.
    var uploaded = 0;
    while (uploaded < _staging.Length &&
           _terrain.Chunks.TryDequeue(out var rect))
    {
        UploadChunk(_staging[uploaded], _pageTexture, rect);
        uploaded++;
    }
}

private void UploadChunk(Texture2D staging, Texture2D target, RectInt rect)
{
    WriteRegion(staging.GetPixelData<Color32>(0), _chunkSize,
                rect, rect.xMin, rect.yMin);
    staging.Apply(false);

    // GPU-side copy of just this chunk into the page texture.
    Graphics.CopyTexture(staging, 0, 0, 0, 0, rect.width, rect.height,
                         target, 0, 0, rect.xMin, rect.yMin);
}

A player controller that reads the page

The character doesn't use Unity physics. It moves one pixel at a time and checks the terrain directly: solid cells block from every side, one-way cells only stop you when you fall onto them from above.

Documents have very different line spacing, and a jump that works on a double-spaced essay is useless on a dense paper. So the game measures the page's typical line pitch and sets the jump to 1.4 lines. Every document stays playable without hand tuning.

// Median distance from each line's top to the line
// directly below it. Lines must overlap horizontally,
// so neighbouring columns don't count.
public static float Estimate(IReadOnlyList<TextLine> lines)
{
    var pitches = new List<int>();
    for (var i = 0; i < lines.Count; i++)
    {
        var upper = lines[i].Bounds;
        var best = int.MaxValue;
        for (var j = 0; j < lines.Count; j++)
        {
            var lower = lines[j].Bounds;
            var pitch = upper.yMax - lower.yMax;
            if (pitch <= 0 || pitch >= best) continue;
            if (Mathf.Min(upper.xMax, lower.xMax) <=
                Mathf.Max(upper.xMin, lower.xMin)) continue;
            best = pitch;
        }
        if (best != int.MaxValue) pitches.Add(best);
    }
    if (pitches.Count == 0) return 0f;
    pitches.Sort();
    return pitches[pitches.Count / 2];
}

Architecture you can test

The project is split into nine assembly definitions: Core, Pdf, Terrain, Physics, Gameplay, UI, Platform, Audio and Bootstrap. An architecture test reads the assembly files and fails if a module references one it shouldn't, so the dependency rules can't quietly erode.

The simulation code (terrain, rockets, black hole, flying letters, letter monsters) is plain C# with no MonoBehaviour, so it runs in more than 300 edit-mode tests without entering Play mode. Systems that run every frame use fixed slot counts and don't allocate.

Design questions I'm testing

Building this brought me back to a question from Game Studies: what does a mechanic change beyond the immediate action?

Here, firing a weapon changes more than a target. It can open a route, destroy a platform you might need, and leave behind letters that become another threat. Letters that come to rest bake back into the page as new platforms, or gather into a monster. I want to see how those consequences interact.

There is also a player-learning question. When do players realise the flying letters are more than visual effects? Can they connect their own destruction to the enemies that follow? Thinking about what players can discover through the systems I build has become the most interesting part of the project.

Still a work in progress. Even after turning my reading into a game, I still have to deal with the consequences of skipping some paragraphs.
